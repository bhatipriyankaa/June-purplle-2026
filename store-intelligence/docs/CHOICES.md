# Engineering Decisions

## YOLOv8 Selection

YOLOv8 was selected as the primary object detection model because it provides a strong balance between detection accuracy, inference speed, and ease of integration.

Reasons for selection:

* Real-time performance on standard hardware.
* Strong person detection accuracy.
* Simple Python integration.
* Actively maintained ecosystem.
* Suitable for rapid prototyping during the hackathon.

Alternative detector architectures such as Faster R-CNN and DETR were considered less suitable due to higher inference costs and integration complexity.

---

## ByteTrack Selection

ByteTrack was selected for multi-object tracking.

Reasons for selection:

* Strong tracking performance in crowded environments.
* Maintains stable identities across frames.
* Lightweight integration with YOLO detections.
* Minimal tuning requirements.

The tracker enables visitor identities to persist across multiple frames, reducing duplicate counting and improving event quality.

---

## FastAPI Selection

FastAPI was selected for backend API development.

Reasons for selection:

* Automatic Swagger documentation.
* Fast implementation speed.
* Native Pydantic validation.
* High performance asynchronous framework.
* Production-ready API structure.

FastAPI allowed rapid development of ingestion and analytics services while maintaining clear API contracts.

---

## Event Schema Design

A structured event schema was adopted to standardize analytics generation.

Each event contains:

* Event Type
* Visitor Identifier
* Store Identifier
* Camera Identifier
* Timestamp

This schema can be extended in future versions to support:

* Age prediction
* Gender prediction
* Staff exclusion
* Group detection
* Customer journey tracking

---

## Storage Strategy

### CSV Storage

CSV storage was selected because:

* Simple to inspect manually.
* Easy to export.
* Lightweight.
* Suitable for hackathon-scale workloads.

### JSONL Storage

JSONL storage was selected because:

* Matches event-streaming patterns.
* Supports incremental event ingestion.
* Easy integration with downstream analytics systems.
* Compatible with large-scale event processing pipelines.

---

## API Architecture Decisions

The backend exposes REST APIs for both ingestion and analytics.

Implemented APIs:

* GET /health
* POST /events/ingest
* GET /metrics
* GET /funnel
* GET /anomalies

This separation allows event producers and analytics consumers to operate independently.

---

## Staff Exclusion Strategy

The billing camera frequently captures store associates performing operational tasks.

A production-grade implementation would exclude staff members using:

* Persistent identity tracking
* Appearance embeddings
* Employee schedules
* Restricted-zone rules

Due to hackathon time constraints, all detected persons are emitted as events and staff exclusion is documented as a future enhancement.

---

## Re-entry Handling

The system uses persistent tracking identities generated by ByteTrack.

Within a single camera session, repeated detections of the same tracked identity are not emitted as new visitor events.

Future versions could support cross-camera re-identification and long-term visitor re-entry detection.

---

## Tradeoffs

Several engineering tradeoffs were made:

* Simpler event storage instead of distributed databases.
* Single-camera tracking instead of full store-wide identity matching.
* Lightweight anomaly detection instead of machine-learning-based anomaly models.
* Billing-camera event generation instead of direct POS integration.

These decisions maximize reliability and end-to-end completeness within the hackathon timeframe.
